## 二、最佳实践（已调研，附来源）
- **主动限流（令牌桶/漏桶）** 比被动重试更优——在触发 429 之前就把速率压在阈值以下。（apipark《Handling Rate Limited》、ergonode《Best Practices》）
- **指数退避 + 全抖动（full jitter）**：`wait = random(0, base·2ⁿ)`，避免大量客户端同步重试形成「惊群」。（Postman《HTTP 429》、apipark）
- **优先尊重 `Retry-After` 头**——服务端最清楚自己的限流窗口。
- **熔断器（Circuit Breaker）**：连续失败达阈值→开路暂停请求一段时间→半开探测恢复。（apipark、ergonode）
- **离线优先（offline-first）**：App Shell 缓存 + 网络优先/缓存兜底 + 本地数据兜底。（Chrome Workbox、PWA 文献）

## 三、架构方案
### 新增/重构模块
- `src/rate-limit.js`：**令牌桶 + 并发上限**调度器 `RequestScheduler`。
- `src/circuit-breaker.js`：熔断器（CLOSED / OPEN / HALF_OPEN）。
- `src/api.js`：统一 `apiRequest(path)`，组合「调度 → 退避(全抖动) → 熔断 → 失败分类」。
- `main.js`：消费上述；新增状态机 `online | throttled | degraded`；失败**显式**提示；降级横幅。
- `styles.css`：美化 + 降级横幅 + 骨架屏 + 暗色。
- （可选）`sw.js` + `manifest.webmanifest`：PWA 离线。

### 1) 严格控制请求频率（核心）
- **单次 random**：用户点「抽一签」只发 1 次 `/api/poems/random`，等待返回；彻底消除并发请求风暴。
- **令牌桶**：容量 6，补充速率 3/s（保守，远低于触发 429 的并发量）。
- **并发上限**：`/api/poems/random` 同时最多 2 个在途。
- **单飞（single-flight）**：`/api/types`、`/api/dynasties` 只拉一次并缓存。
- **退避（全抖动）**：base 300ms，×2ⁿ，上限 8s，有 `Retry-After` 用之。
- **围栏**：熔断开路期间，不再发 random 请求。

### 2) 失败处理（按你的要求：显式提示 + 请稍后重试 / 降级本地）
状态机：
- **ONLINE**：正常。
- **DEGRADED（重试耗尽 / 熔断开路 / 离线）**：
  - 顶部常驻横幅：「⚠ 诗泉接口暂不可用（限流/离线），已切换本地诗词库（70 首）· [重试恢复]」。
  - 抽卡仍可用（本地库 pickLocalOne），筛选照常工作。
  - 「[重试恢复]」按钮：触发半开探测，成功则回 ONLINE 并清横幅。
  - 文案区分：`navigator.onLine === false` → 「网络已断开」；429 → 「接口限流」。

## 五、风险与注意
- **PWA 仅在 http(s) 下生效**：双击 `file://` 打开时 Service Worker 不注册。需以本地服务（如 `npx http-server`）或部署后使用。若坚持「双击即玩」，PWA 降级为「纯本地 JSON 兜底」（不依赖 SW）。
- 令牌桶参数（6/3s）为保守估值；若仍有 429，可据响应头 `X-RateLimit-*` 自适应下调。
